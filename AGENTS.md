# Ultracode Repository Guide

This repository is a Codex CLI plugin that gives Codex a parallel worker orchestration layer. Ultracode fans out real `codex exec` subprocesses for deep code investigation, planning, and review, then returns structured results to the parent Codex thread where the final synthesis and edits happen.

The plugin is designed to bring Claude Workflow-style orchestration primitives to Codex: arbitrary worker prompts, JSON schema validation, concurrency limits, budget tracking, progress events, journaled resume, `parallel`, `pipeline`, loop-until-dry checks, adversarial verification, and optional git worktree isolation. Those primitives are reachable three ways: the fixed-role / `workers_spec` `ultracode_run` fan-out, the declarative `ultracode_pipeline` `steps[]` DAG, and — for imperative control flow — the opt-in Workflow-script runner (`ultracode_script` / `ultracode-cli.js script`), which binds the primitives into a plain async-JavaScript scope.

## Main Components

- `.codex-plugin/plugin.json` declares the plugin metadata, keywords, skills, the `interface` block (display name, capabilities, default prompts, brand color), and the MCP server (via `mcpServers: "./.mcp.json"`). Hooks are declared separately in `hooks/hooks.json` (a `UserPromptSubmit` hook), and the launcher is `scripts/run-node-tool.sh` (wired in through `.mcp.json`, not `plugin.json`).
- `scripts/ultracode-engine.js` is the core orchestration engine. It owns worker spawning, schema validation, concurrency, usage accounting, persisted workflow state, resume, and exported scripted primitives. It also carries a single lazy `runScript` re-export (call-time `require` of the script runner, no require cycle).
- `scripts/ultracode-script-runner.js` is the opt-in imperative Workflow-script runner (`runScript`). It binds the engine primitives into a bound script scope (`agent`, `parallel`, `pipeline`, `phase`, `log`, `budget`, `args`, ...) and journals a `kind: "script"` record. It runs ARBITRARY Node.js in-process with full host privileges — it is NOT a sandbox.
- `scripts/app-server-client.js` is the dependency-free `codex app-server` JSON-RPC client for the opt-in `transport: 'app-server'` path. It frames the server's bare JSON-RPC objects leniently, drives the `initialize -> initialized -> thread/start -> turn/start` handshake, accumulates streamed message text, and normalizes the camelCase token-usage breakdown into the engine's usage shape. It exports `runAppServerTurn` plus an `_internal` (`normalizeUsage`, `classifyMessage`, `extractThreadId`, `extractTurnId`, `embedSchema`, `AppServerConnection`).
- `mcp/server.js` is a dependency-free MCP stdio server exposing `ultracode_plan`, `ultracode_run`, `ultracode_pipeline`, `ultracode_resume`, `ultracode_status`, and (gated) `ultracode_script`.
- `scripts/ultracode-cli.js` is a CLI wrapper over the same engine with `plan`, `run`, `pipeline`, `resume`, `status`, and `script` commands.
- `scripts/run-node-tool.sh` resolves the local Node and Codex binaries for MCP and hook execution.
- `hooks/` contains the prompt hook that injects Ultracode guidance when a prompt mentions Ultracode.
- `skills/ultracode/SKILL.md` is the model-facing usage guide for when and how to invoke Ultracode.
- `package.json` defines the test entry point (`"test": "node --test \"test/**/*.test.js\""`); the engine itself stays dependency-free (no production `dependencies`).
- `test/` holds the Node test suite (`*.test.js`), plus `test/fixtures/` (the env-driven `mock-codex.js`, the failing `mock-codex-fail.js`, and the `echo.workflow.js` / `throws.workflow.js` script fixtures) and `test/helpers/env.js` (the mock harness: `withCodexHome`, `withMockEnv`, `withCodexCliPath`, `mockOpts`, `freshSessionDir`, ...). See **Testing** below.
- `examples/` holds runnable Workflow scripts (`budget-loop.workflow.js`, `parallel-reduce.workflow.js`) that can be dry-run for free against the mock Codex.
- `README.md` is the human-facing overview, parity matrix, and usage reference.

## Runtime Behavior

Ultracode workers are real Codex subprocesses, not mocked agents. Worker output is schema-validated when a schema is provided, usage is aggregated from Codex JSON events, and workflow state is written under `$CODEX_HOME/ultracode/runs/`.

Temporary schemas, last-message files, and isolated worktrees are created under the OS temp directory. They should not create tracked files in this repository.

By default every worker is a fresh, ephemeral `codex exec` (no session persisted). An opt-in warm executor keeps a Codex session warm across turns via `codex exec resume <session_id>`: `spawnWarmWorker(initialPrompt, opts)` returns a `{ sessionId, result, turn(prompt) }` handle, and `runPipeline(items, stages, { warm: true })` reuses one warm session per item across stages (warm reuse is per item; cross-item fan-out stays parallel). The pipeline DAG (`ultracode_pipeline` / `pipeline`) takes an `executor` (`cold` | `resume` | `fork`) at the top level and per step. Warm context is a pure latency/cost optimization: a resume turn the CLI cannot honor (unknown/expired rollout via `no rollout found for thread id`, non-zero exit, or missing last-message) transparently falls back to the identical cold `codex exec` and logs `resume-fallback`. The `resume` subcommand rejects `--output-schema`/`-s`/`-C`/`--add-dir`/`-p`, so schema is enforced via prompt-injection + the existing post-hoc validation/retry and sandbox/cwd are inherited from the original persisted session. `executor: 'fork'` is a documented stub: `codex fork` is interactive-TUI-only, so it logs `fork-unsupported` and runs cold. With nothing opted in, the cold fan-out (still `--ephemeral`) is byte-for-byte unchanged.

The worker **transport** is independently opt-in. `transport: 'exec'` (default; also `ULTRACODE_TRANSPORT` env) is today's `codex exec --json` JSONL scraping, unchanged. `transport: 'app-server'` instead spawns the versioned `codex app-server` JSON-RPC server (`scripts/app-server-client.js`), drives `initialize -> initialized -> thread/start -> turn/start`, accumulates `item/agentMessage/delta` text, and normalizes the camelCase `thread/tokenUsage/updated` breakdown into the engine's snake_case usage shape — returning the same `{ execResult, value }` contract so usage accounting, schema retries, worktree isolation, and persistence are untouched. The app-server emits BARE JSON-RPC objects (no top-level `jsonrpc` field), so the client frames leniently. Any app-server failure (initialize/protocol/timeout) transparently falls back to the exec path and emits a `worker.transport_fallback` event, unless `transport_strict: true`. `transport: 'exec-server'` is reserved and throws an explicit not-implemented error (the client seam is generic enough to host it later). The transport is journaled into `workflow.options` only when non-default, so a plain run's options object is byte-identical to before.

**Transient-error retry / bounded backoff** is opt-in and off by default. On a non-zero `codex exec` exit the engine classifies the failure via `classifyCodexError`: permanent patterns (auth, bad flag, schema, and timeouts) never retry; retryable patterns (HTTP 429/5xx, rate-limit, network errno) do; the classifier is **fail-closed**, so any unrecognized non-zero exit is treated as permanent. When `max_retries > 0` a retryable failure is re-spawned with exponential **full-jitter** backoff (`backoffDelay`, capped at `max_delay_ms`), emitting a `worker.retry` event and a `transient-retry` log per attempt. Knobs: `max_retries` (default `0` — byte-identical to the pre-retry engine), `base_delay_ms` (`500`), `max_delay_ms` (`30000`), `retry_jitter` (`true`). These transient retries are a **separate counter** from schema-validation retries (one never consumes the other). The knobs flow through `ultracode_run` / `ultracode_pipeline` / `resume` and are journaled into `workflow.options` only when `max_retries > 0`, so a default run's options object is unchanged.

**Cancellation** is a first-class engine capability, not just a CLI concern. Each per-run `ctx` owns an internal `AbortController`; an external `opts.signal` is mirrored into it (`createContext`), and `ctx.signal` threads into every exec spawn and app-server turn. Aborting uses the same `SIGTERM -> 5s -> SIGKILL` kill ladder as the timeout path; an in-flight backoff short-circuits via `abortableDelay`. A cancelled worker does not throw — it resolves to a non-throwing record with `status: "cancelled"` (`cancelledWorker`), and `finalizeRecord` reports the whole run `cancelled` when every worker was cancelled. The CLI's `runCancellable` (see SECURITY below) installs a scoped one-shot `SIGINT` handler that aborts via this shared `ctx`; it can be opted out with `--no-cancel-on-sigint` or `ULTRACODE_NO_SIGINT`, and only wraps `run` / `pipeline` / `resume` / `script` (not `plan` / `status`). A second Ctrl-C hard-exits `130`.

`mcp/server.js` honors MCP progress: when a `tools/call` for `ultracode_run` / `ultracode_pipeline` / `ultracode_script` supplies `params._meta.progressToken`, the server builds an `on_event` sink that emits `notifications/progress` `{ progressToken, progress, message }` on the same connection (with a monotonically increasing `progress` integer, `total` omitted) until the final result. Absent the token, no `on_event` is wired and behavior is identical to before.

The Workflow-script runner (`scripts/ultracode-script-runner.js`, `runScript(input)`) is the imperative analogue of Claude Code's in-process Workflow tool. It XOR-validates `source | path` (path is read by contents, dirname-independent), builds one shared per-run engine `ctx` (concurrency / budget / max_agents / `ULTRACODE_DEPTH` / `on_event` / `signal`), and compiles the script body with the `AsyncFunction` constructor whose named parameters are the bound scope: `agent` (->`value`|`null`), `spawnWorker` (->full record), `parallel`, `pipeline` (VARIADIC `items, ...stages` -> `runPipeline(items, stages, {ctx})`; passing stages positionally would silently null every item), `loopUntilDry`, `adversarialVerify`, `log`, `phase` (closure-tracked default phase), `workflow` (depth-guarded nested `runScript`; throws past depth 1), plus `budget`, `args`, `ctx`, `WORKER_SCHEMA`, `VERDICT_SCHEMA`. A source transform tolerates ES-module sugar (`export default <expr>` -> captured return; leading `export const|let|var|async|function|class` -> bare decl, both line-anchored) and prepends a `"use strict";` prelude as hygiene. The result is a journaled `kind: "script"` record (`id`, `kind`, `status`, `started_at`/`completed_at`, `duration_ms`, `cwd`, `options`, `state_path`, `workers: []`, `result`, `events`, `aggregate_usage`, `warnings?`, `error?`) written to `$CODEX_HOME/ultracode/runs/`; a throwing or syntactically broken script is caught and journaled `status: "failed"` with partial events (the host never crashes). Records carry `workers: []` so `resumeWorkflow` degrades to a clean no-op and `readWorkflow` / `ultracode_status` read them unchanged. The runner also installs a scoped `process.on("unhandledRejection")` listener for the duration of the run and yields one macrotask (`setImmediate`) so any orphaned (fire-and-forget) promise rejection is delivered rather than crashing the long-lived host (e.g. the MCP server); captured orphans are surfaced as `record.warnings` (`["unhandled promise rejection: ..."]`) plus an `unhandled-rejection` log event. A script that returned a value but leaked a rejection is still journaled `status: "completed"` with `warnings`.

SECURITY (this is NOT a sandbox): `runScript` executes ARBITRARY Node.js IN-PROCESS in the host with FULL host privileges (it can `require()` anything, read `process.env` secrets including Codex tokens, write any file, and spawn shell-running workers). The `AsyncFunction` transform is purely ergonomic — it provides no isolation. Trust level equals `node <file>.js`. Gating: the CLI `script <path>` command is ALLOWED BY DEFAULT (the operator ran a local file from their own shell); the MCP `ultracode_script` tool is DISABLED unless `ULTRACODE_ALLOW_SCRIPT=1` (checked at dispatch time so tests can toggle it), and when disabled returns a non-throwing `isError` content result naming the env var. When enabled it prefers an operator-controlled file `path` over inline `source`. The runner never auto-dumps `process.env`; the persisted record/events may capture whatever the script logs/returns or a worker prints to stderr, so run files are SENSITIVE. The engine's per-run caps (one limiter, `budget_tokens` soft gate, `max_agents`, `ULTRACODE_DEPTH` nesting guard) bound the workers a script spawns but not the script itself. No `vm`/`child_process`/`worker_threads` isolation exists today; true isolation is noted as future hardening. The CLI wraps the run in the existing `runCancellable` so Ctrl-C aborts via the shared `ctx` (scoped, one-shot SIGINT handler, removed in `finally`; opt-out via `--no-cancel-on-sigint` / `ULTRACODE_NO_SIGINT`); no permanent global signal handler is installed.

## Testing

The suite runs entirely offline against a mock Codex binary — **tests never call the real, paid `codex` CLI**.

- Run everything with `npm test` (which runs `node --test "test/**/*.test.js"`) or directly with `node --test "test/**/*.test.js"`. Run a single file with `node --test test/<file>.test.js`.
- `test/fixtures/mock-codex.js` is an env-driven stand-in for `codex` (it understands `exec`/`resume`/`app-server` and emits the same JSON event shapes). Tests point the engine at it via `codex_bin` / `CODEX_CLI_PATH` (the `app-server-client.js` header makes the same rule explicit: tests MUST point the bin at a mock app-server, never the real CLI). Its behavior is shaped by env vars such as `MOCK_CODEX_RESPONSE`, `MOCK_CODEX_USAGE`, `MOCK_CODEX_EXIT`, `MOCK_CODEX_SLEEP_MS`, `MOCK_CODEX_FAIL_TIMES`, `MOCK_CODEX_SESSION_DIR`, `MOCK_CODEX_REJECT_RESUME`, and the app-server toggles `MOCK_APPSERVER_FAIL_INIT` / `MOCK_APPSERVER_NO_THREAD`. `test/fixtures/mock-codex-fail.js` is a deliberately failing variant. These `MOCK_*` vars are test-only and are not part of the product runtime.
- `test/helpers/env.js` is the harness (`withCodexHome`, `withMockEnv`, `withCodexCliPath`, `mockOpts`, `freshSessionDir`, ...). It sandboxes each run's `CODEX_HOME` to a fresh temp directory, so no run files land in this repo.
- The `examples/*.workflow.js` scripts are runnable for free against the mock. Each carries a header comment with its invocation, e.g.:

  ```
  CODEX_CLI_PATH=test/fixtures/mock-codex.js \
  node scripts/ultracode-cli.js script examples/budget-loop.workflow.js \
    --budget-tokens 5000 --max-agents 6 --concurrency 2
  ```

  Always set `CODEX_HOME` to a temp dir and point `CODEX_CLI_PATH` (or `codex_bin`) at the mock when running examples or tests so nothing hits the real CLI.

## Development Notes

- Keep the engine dependency-free unless there is a strong reason to change that.
- Preserve the existing MCP and CLI contracts when adding new orchestration features.
- Prefer explicit failures and logged events over silent fallbacks.
- Keep worker execution parallel by default; add throttling only when limits have been measured.
- The script runner top-level-`require`s the engine; the engine must NOT top-level-`require` the runner (it uses a lazy call-time `require` for its `runScript` re-export). Keep that direction to avoid a require cycle. The MCP server and CLI `require` the runner directly.
- The MCP `ultracode_script` gate (`ULTRACODE_ALLOW_SCRIPT=1`) is checked at dispatch time, not at `tools/list` time; do not weaken it. Never auto-dump `process.env` into events, and keep treating run files as sensitive.
- Do not commit local `.claude/` files or `.DS_Store`.
